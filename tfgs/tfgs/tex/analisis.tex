\subsection{Descripción}

\subsubsection{Actores}

\begin{itemize}
	\item \textbf{Usuario}: Es el actor principal y más activo. Representa a la persona que interactúa con los teclados virtuales.
	\item \textbf{Unity}: Es un actor secundario que solo actúa en el arranque del sistema. Representa al motor de desarrollo utilizado.
\end{itemize}

\subsubsection{Casos de uso identificados}

\begin{enumerate}
	\item \textbf{Escribir en teclado}:
		\begin{itemize}
			\item Es la acción estándar que se espera de cualquier teclado que se precie.
			\item Existe una interacción directa con el \textit{Usuario}.
		\end{itemize}
	\item \textbf{Cambiar tipo de teclado}:
		\begin{itemize}
			\item Es la acción de cambiar entre el uso de teclados físicos o los planos.
			\item Existe una interacción directa con el \textit{Usuario}.
			\item Existe una interacción directa con \textit{Unity} al arranque del sistema que deja el teclado físico por defecto.
		\end{itemize}
	\item \textbf{Cambiar de idioma}:
		\begin{itemize}
			\item Es la acción de cambiar el idioma del teclado en uso.
			\item Existe una interacción directa con el \textit{Usuario}.
			\item Existe una interacción directa con \textit{Unity} al arranque del sistema para poner el idioma de tu SO o, en su defecto, el inglés
			.
		\end{itemize}
	\item \textbf{Modificar teclas}:
	\begin{itemize}
		\item Algunos idiomas necesitan modificar las teclas para poder utilizar acentos, mayúsculas y otras posibles características.
		\item Es una extensión del caso de uso de \textit{Escribir en teclado} por lo que también requiere la intervención del \textit{Usuario}.
	\end{itemize}
\end{enumerate}

\subsubsection{Relaciones}

\begin{itemize}
	\item El \textit{Escritor} hace uso del \textit{InputField} para poder mostrar lo que se escribe.
	\item El \textit{Controlador} tiene diversos objetos de la clase \textit{Teclado} para controlar.
	\item El \textit{Teclado} está formado por varios objetos de la clase \textit{Tecla}.
	\item La \textit{Tecla} usa al \textit{Boton} para escuchar eventos.
	\item El \textit{Botón}, como ya hemos dicho, escucha eventos concretos de la clase \textit{Evento}.
	\item El \textit{Evento} llama a funciones del \textit{Teclado}.
	\item El \textit{Teclado} hace uso del \textit{Escritor} para realmente escribir.
\end{itemize}

\subsection{Principios SOLID que se siguen}

\subsubsection{El Principio de responsabilidad única (Single Responsibility Principle - SRP)}

``Cada clase tiene que tener una única responsabilidad y una sola razón para cambiar.''

Este principio dice que una clase debe tener solo una responsabilidad un motivo para cambiar, o sea, tener una única tarea.

Hasta cierto punto esto se cumple con las separaciones de la lógica del teclado en \textit{Teclado}, la lógica de una tecla en \textit{Tecla}, la parte física de una tecla en \textit{Boton}, el control general en el \textit{Controlador} y la escritura en el \textit{escritor}.


\subsubsection{El Principio Abierto-Cerrado (Open/Closed Principle - OCP)}

``Las clases tienen que estar abiertas a la extensión pero cerradas a la modificación.''

Este principio nos indica que el código tiene que permitir añadir funcionalidades nuevas (abierto a la extensión) sin tener que modificar las clases existentes (cerradas a la modificación), reduciendo el riesgo de introducir errores en el sistema.

El uso de la clase \textit{Evento} permite la extensión de comportamientos sin tener que modificar el código de \textit{Boton}.

En \textit{Tecla}, con el uso de la variable ``formas'', permitiría la incorporación de varios idiomas sin necesidad de modificarse internamente. Por otro lado, y siguiendo la idea de los idiomas, el \textit{Teclado} está abierto a recibir extensiones necesarias para la correcta implementación de nuevos idiomas, pero sin modificar lo anterior.

En cuanto al \textit{Controlador}, en este si que se tendrían que hacer cambios en el código para la implementación de nuevos idiomas, por lo que en este no se cumple.

\subsubsection{El Principio de sustitución de Liskov (Liskov Substitution Principle - LSP)}

``Las clases derivadas tienen que poder sustituir sus clases bases sin romper el comportamiento del programa.''

Esto explica que, si una clase derivada altera el comportamiento esperado de la clase base, puede provocar errores inesperados en otras partes del sistema. Es decir, si una clase A es la base de una clase B, cualquier instancia de B tiene que comportarse como una instancia de A sin romper el código.

En cuanto a este principio no puedo comentar nada, ya que, como se ve en el diagrama de clases, no hay herencia de ningún tipo, por lo que no hay clases derivas de otras base que pueda o no respetar este. Por esto, este principio es como el gato de schrodinger, se cumple y no al mismo tiempo.

\subsubsection{El Principio de segregación de interfaz (Interface Segregation Principle - ISP)}

``Es mejor tener interfaces pequeñas y específicas que una única interfaz grande.'' 

Esta definición del principio explica que si una interfaz obliga una clase a implementar métodos que no necesita, significa que está mal diseñada. Es preferible dividirla en interfaces más pequeñas y enfocadas.

\subsubsection{El Principio de inversión de dependencia (Dependency Inversion Principle - DIP)}

``Las dependencias tienen que estar en abstracciones, no en clases concretas.''

Este principio significa que las clases de alto nivel no tienen que depender de las de bajo nivel. En cambio, todas tienen que depender de abstracciones (interfaces o clase abstractas) para hacer el código más flexible y fácil de adaptar.

La clase \textit{Botón} usa objetos de tipo \textit{Evento} para encapsular conductas. Esto constituye una modalidad fundamental de inversión de dependencias, dado que la lógica del botón se asigna a los objetos que llevan a cabo dichas acciones y no en unas concretas. Así, la clase \textit{Botón} puede ser reutilizada y ampliada con facilidad sin tener que conocer los pormenores específicos de cada evento.

\begin{itemize}
	\item Descripción detallada de escenarios típicos de uso:
	\begin{itemize}
		\item Escenario 1: Cambio de idioma en el teclado virtual
		\begin{itemize}
			\item El usuario inicia la aplicación de realidad virtual.
			\item El teclado aparece con el idioma del sistema operativo si coincide con uno de los idiomas disponibles, si no, aparece en inglés.
			\item El usuario selecciona el menú de configuración del teclado.
			\item El usuario elige uno de los seis idiomas disponibles.
			\item El teclado virtual cambia al idioma seleccionado.
		\end{itemize}
		\item Escenario 2: Cambio de tipo de teclado (físico y plano)
		\begin{itemize}
			\item El usuario inicia la aplicación de realidad virtual.
			\item El teclado virtual aparece en su configuración predeterminada, que es el teclado físico.
			\item El usuario pulsa el botón de cambio de teclado.
			\item El teclado virtual cambia de una representación física a una plana.
		\end{itemize}
	\end{itemize}
	
	\item Ejemplos prácticos de cómo se utilizará el sistema:
	\begin{itemize}
		\item Ejemplo 1: Uso en un juego de RV en varios idiomas
		\begin{itemize}
			\item El usuario crea el juego y necesita usar el Asset.
			\item El usuario selecciona el tipo de teclado (físico o plano) según su preferencia.
			\item El usuario cambia la forma de cambiar de idioma para adaptarlo a su propio menú.
			\item El usuario configura el juego y el teclado según sus necesidades.
		\end{itemize}
		
		\item Ejemplo 2: Redacción de datos en un programa de RV
		\begin{itemize}
			\item El usuario crea el programa y se descarga el Asset.
			\item El usuario pone el teclado virtual en el idioma deseado.
			\item El usuario selecciona el tipo de teclado (físico o plano) según su preferencia.
			\item El usuario configura la introducción de datos para usar el teclado.
		\end{itemize}
		
		\item Ejemplo 3: Simulación de mecanografía en RV
		\begin{itemize}
			\item El usuario crea el simulador y se descarga el Asset.
			\item El usuario pone el teclado virtual en el idioma deseado.
			\item El usuario selecciona el de teclado físico o plano.
			\item El usuario configura la introducción de datos para usar el teclado.
			\item El usuario configura los objetivos mecanográficos necesarios.
		\end{itemize}
	\end{itemize}
\end{itemize}
